# Go 与 Rust 的设计过程

本文整理两门语言的设计与实现过程，作为语言研究的方法参考。历史事实与方法总结分别列出；这些经验不定义 Fini 的语言规则。

资料查阅日期：2026-10-09。来源均为项目官方文档或官方回顾。

## Go：小团队设计与早期原型

### 初期过程

| 时间 | 工作 |
| --- | --- |
| 2007 年 9 月 | 从工程问题出发讨论语言目标，逐步形成方案。 |
| 2008 年 1 月 | 开始用生成 C 的探索性编译器检验想法。 |
| 2008 年 3 月 | 仓库最早的提交记录是一份规范草案。 |
| 2008 年 7 月 | 项目已有规范、编译器、少量库和测试程序。 |
| 2009 年 11 月 | 公开开源，继续通过社区使用和修改完善语言。 |
| 2012 年 3 月 | 发布 Go 1，转向明确的稳定性承诺。 |

2007 年的目标讨论与 2008 年的探索编译器见 [Go FAQ：项目历史](https://go.dev/doc/faq#history)。规范提交和早期项目内容见 [How Go was made](https://go.dev/talks/2015/how-go-was-made.slide)。开源后的修改及 Go 1 的稳定化见 [Toward Go 2](https://go.dev/blog/toward-go2)。这些日期描述不同的活动，不应把最早的规范提交理解为原型实现的开始。

### 设计方法

初期设计通过邮件和当面讨论推进。新增特性需要三位作者都认为必要，多数提议被舍弃。规范包含具体程序，例如素数筛；语言设计、编译器和测试程序在早期就共同演进。[How Go was made](https://go.dev/talks/2015/how-go-was-made.slide)

有些设计需要较长时间才能形成，例如切片。团队没有等待所有问题结束才开始实现，而是在已有实现和程序的基础上继续修改。Go 1 之前仍有频繁的不兼容变化，稳定性是后续阶段的明确承诺。[How Go was made](https://go.dev/talks/2015/how-go-was-made.slide)、[Toward Go 2](https://go.dev/blog/toward-go2)

## Rust：实现反馈与逐步稳定

### 1.0 前的迭代

接近 Rust 1.0 时，语言和库仍在调整。2015 年 2 月的发布计划记录了整数越界语义、路径和 IO API 等变化。新的路径和 IO API 已经实现，但团队认为使用经验不足，因此增加一轮 alpha，让社区继续试用，再决定是否稳定。[Rust 1.0: status report and final timeline](https://blog.rust-lang.org/2015/02/13/Final-1.0-timeline/)

这说明代码已经实现、设计文档已有描述，并不等于设计具备足够的稳定性证据。

### RFC 与稳定化

RFC 是公开征求意见的设计提案。较大的语言变化需要说明动机、具体设计、缺点和替代方案，再通过讨论修订。小型修复和文档改写不必经过同样的设计流程。[Rust RFC Book](https://rust-lang.github.io/rfcs/)

RFC 流程是在 Rust 1.0 前的一年里引入和完善的项目治理方式，不是所有语言从零起步时都必须复制的流程。[Rust in 2016](https://blog.rust-lang.org/2015/08/14/Next-year/)

提案通过后仍需实现和验证。正式稳定前，团队要求检查实现完整性、测试覆盖和未解决问题，说明实现过程中对设计的修改，并补充语言参考文档。[Rust 语言团队：稳定化流程](https://lang-team.rust-lang.org/how_to/stabilize.html)

可以将这个成熟阶段的过程概括为：

```text
动机与设计提案
    ↓ 讨论、比较替代方案、修订
实验实现与使用反馈
    ↓ 测试、处理边界、调整设计
稳定化评审与文档
```

这只是流程概括，不表示 Rust 从最初就采用了完整的 RFC 制度，也不表示每次变更都按完全相同的步骤进行。

## 方法总结

以下是对上述资料的归纳，用于指导小规模语言研究，不是某一项目规定的统一流程。

| 方法 | 实际做法 |
| --- | --- |
| 从目标和任务出发 | 先说明语言解决什么问题，用少量程序展示需求。 |
| 先定义一小块行为 | 写出规则、正常结果和非法程序，再实现对应部分。 |
| 尽早运行原型 | 不必等完整语言设计结束，先检验最小模型。 |
| 设计和实现交替推进 | 用使用反馈、测试与反例修订规则。 |
| 优先验证核心约束 | 技术风险应通过针对性实验检验，不能只依靠文档。 |
| 扩展需要证据 | 新能力应有具体任务、代价分析和实现经验。 |
| 区分草案与稳定承诺 | 原型规则可以修订；稳定需要更充分的测试和使用经验。 |

## Fini 的原型边界

Fini 的 Go 转换原型可验证解析、名称检查、类型检查、求值和错误行为。Go 的运行时内存回收不能证明 Fini 的无 GC 释放目标成立。

固定大小的整数与布尔值也不足以检验动态存储回收。后续实验需要包含动态大小的数据、名称复用、函数返回和分支汇合，分析哪些存储仍被使用，以及释放操作在何处执行。参见 [基础构造与内存释放](01-foundations.md)。

这个阶段可以使用很小的实验实现，不要求先完成完整编译器、标准库或所有语言特性。
